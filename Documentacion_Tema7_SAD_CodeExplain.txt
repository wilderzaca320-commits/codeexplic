================================================================================
 RESUMEN EJECUTIVO
================================================================================

 CodeExplain es una aplicacion web local que opera en el puerto 3100 y se
 arranca con `npm run dev` (tsx server.ts). El frontend (React 19 + TypeScript +
 Vite 8 + Tailwind 4) ofrece 12 vistas y tres niveles de audiencia
 (basico / intermedio / avanzado). El backend (Express 4) expone tres endpoints
 POST bajo /api/gemini/* y delega la generacion a Gemini 2.5 Flash cuando existe
 GEMINI_API_KEY; si no existe o falla, responde un motor heuristico local.

 Medidas tomadas hoy sobre el codigo:
   - src/: 20 archivos (17 .tsx + 3 .ts), 5 988 lineas.
   - server.ts: 251 lineas. Total de codigo propio: 6 239 lineas.
   - 12 vistas, 3 componentes compartidos, 9 tipos de dominio, 7 conjuntos de
     datos de ejemplo en mockData.ts (447 lineas).
   - Endpoints REALIZADOS: 3. Endpoints que el cliente llama y el servidor NO
     implementa: 2 (/api/analyze, /api/analyze-url). Endpoint documentado en
     Fases 2/4/6 pero ausente: 1 (/api/health).

 Decision arquitectonica dominante: monolito modular de dos capas desplegado como
 un unico proceso, con degradacion elegante (fallback) como mecanismo principal
 de disponibilidad. El estilo "microservicios" que muestra la pantalla de
 diagramas NO es la arquitectura de CodeExplain, sino un ejemplo de salida.

 Riesgo arquitectonico numero uno: desconexion entre la capa de presentacion y
 el motor de analisis. `src/lib/analyzeProject.ts` construye un digest real desde
 un ZIP JSZip (290 lineas), pero `UploadModal.tsx` nunca lo invoca: usa un
 setInterval de 900 ms y datos fijos (UploadModal.tsx:43-78). Ademas, las dos
 funciones que si llaman al servidor (analyzeProject.ts:257 y :270) apuntan a
 rutas no registradas en server.ts. Esto se detalla en 6.8.

 2.5. TRADE-OFFS EXPLICITOS
   - CAP: al ser un sistema centralizado de un solo nodo, elige consistencia
     fuerte dentro del proceso (estado en React) y no necesita resolver
     particiones de red. Si se distribuyera, la prioridad seria disponibilidad
     (fallback) antes que consistencia entre replicas de historial.
   - Costo vs complejidad vs time-to-market: se eligio monolito + plantillas
     fijas en lugar de microservicios + BD + buses. Resultado: costo operativo
     minimo y entrega rapida, a cambio de simulacion en varias vistas y deuda
     funcional documentada en 6.8.
   - Calidad de IA vs disponibilidad: Gemini primero, heuristica despues
     (ADR-03). Se sacrifica riqueza de respuesta cuando no hay key o hay cuota
     agotada, pero nunca se corta la sesion.
   - Privacidad vs profundidad: enviar solo un digest protege el codigo, pero
     limita el analisis a estadisticas y muestra de texto (no AST real).

 3.1. VISTA LOGICA (estructura conceptual)
   Patron real: MONOLITO MODULAR EN CAPAS con SPA desacoplada por HTTP.
   No es hexagonal, no es DDD implementado, no es microservicios.

   +-------------------------------------------------------------------------+
   | CAPA DE PRESENTACION (navegador, React 19)                              |
   |  App.tsx (router por estado)                                            |
   |  +-- components/ : Sidebar | Header | UploadModal                       |
   |  +-- views/      : 12 pantallas (VisionGeneral, ChatAsistenteIA, ...)   |
   |  +-- types/      : 9 tipos del dominio (contrato compartido)           |
   |  +-- data/       : mockData.ts (7 datasets de demostracion)            |
   |  +-- lib/        : analyzeProject.ts (digest ZIP, sin cablear)         |
   +-------------------------------+-----------------------------------------+
                                   | fetch JSON (solo ChatAsistenteIA)
   +-------------------------------v-----------------------------------------+
   | CAPA DE API / APLICACION (Express, server.ts, un proceso)              |
   |  express.json(10mb) -> POST /api/gemini/chat | /explain | /document    |
   |  LEVEL_PROMPTS (basico/intermedio/avanzado)                            |
   |  Cliente GoogleGenAI (si hay key)  +  motor heuristico (fallback)      |
   |  Vite middleware (dev) o express.static(dist) (prod)                   |
   +-------------------------------------------------------------------------+
   Reglas de dependencia observadas:
     - las vistas dependen de types/ y data/, nunca de Express;
     - el servidor no importa codigo de src/ (comparte contrato por convencion,
       no por modulo TypeScript: no hay tipos compartidos reales entre capas);
     - el estado del proyecto vive en App.tsx:27-31 y se pasa por props.

   Patrones presentes:
     - State Router (ADR-08) en lugar de React Router.
     - Proveedor de contexto por props (project, level) en lugar de Context API.
     - Strategy/Plantilla por nivel de audiencia: LEVEL_PROMPTS.
     - Fallback pattern: try Gemini -> catch -> heuristica.
     - Adapter de salida: Blob + <a download> para exportar artefactos.
   Patrones ausentes (no inventar): Repository, Unit of Work, DI container,
     Circuit Breaker, Outbox, Saga, CQRS, Event Sourcing, Service Mesh.

 3.2. VISTA DE PROCESOS (comunicacion en tiempo de ejecucion)
   Flujo REAL del chat (unico flujo que cruza la red hoy):

   Usuario -> ChatAsistenteIA (escribe) -> setMessages (optimista)
           -> POST /api/gemini/chat {message, level, projectContext}
           -> server.ts valida `message` (400 si falta)
           -> selecciona LEVEL_PROMPTS[level]
           -> [alt: hay clave y Gemini responde]
                GoogleGenAI.models.generateContent("gemini-2.5-flash")
                -> {reply, level, model:"gemini-2.5-flash"}
              [else: sin clave / excepcion]
                motor heuristico por palabra clave -> {reply, level,
                model:"codeexplain-core-v2.4"}
           -> setMessages con la respuesta -> scroll automatico.
   Concurrencia: un unico event loop de Node; no hay hilos, locks ni colas.
   El "Redlock / TTL 5000 ms" que aparece en las respuestas avanzadas es
   CONTENIDO GENERADO, no mecanismo del sistema (server.ts:85, DiagramasC4UML.tsx:43).

   Flujo de ingesta SIMULADO (UploadModal.tsx:43-78):
   abrir modal -> elegir pestaña -> pulsar "Iniciar" -> setInterval(900 ms)
   -> 4 mensajes de progreso preescritos -> setTimeout(800 ms)
   -> crear ProjectWorkspace con astHealth: 88, debtHours: 12, spofCount: 1
   -> inyectarlo en App -> cerrar modal. No hay clonacion, no hay AST, no hay fetch.

   Flujo de ingesta CONSTRUIDO PERO SIN CONECTAR (analyzeProject.ts):
   File ZIP -> JSZip.loadAsync -> filtrar SKIP_DIRS -> priorizar package.json,
   README, configs y entrada -> leer hasta 300 archivos/4 MB -> SLOC por
   extension -> extraer dependencias (package.json, requirements.txt, go.mod,
   Cargo.toml) -> construir textSample de 48 KB -> analyzeDigest() ->
   POST /api/analyze. El servidor NO registra /api/analyze (server.ts:39,109,156).
   Resultado: este flujo termina en 404 si se activa.

   Sincronia/asincronia: todo es asincrono a nivel de red (fetch/await); la UI
   usa setInterval/setTimeout solo para animar progreso. No hay Web Workers,
   no hay streaming, no hay websockets.

 4. REGISTRO DE DECISIONES ARQUITECTONICAS (ADR)
================================================================================
   Estados: [R] vigente en codigo | [S] decidida pero implementada a medias |
            [P] planificada, no implementada.

 ADR-01 | Extraccion en el navegador y envio solo del digest .............. [S]
   Contexto/fuerza: ZIP de hasta 200 MB con codigo privado; C-TEC-03, C-REG-01.
   Alternativas: subir el ZIP (descartada por payload y privacidad); parser en
   servidor (descartada por memoria del unico proceso).
   Decision: JSZip en cliente, muestra <= 48 KB.
   Consecuencias: servidor liviano, analisis superficial. El digest existe en
   analyzeProject.ts:167-253, pero UploadModal.tsx no lo llama: la decision
   esta documentada y codificada, no integrada.

 ADR-02 | Backend monolitico Express en un solo proceso ................... [R]
   Contexto: demo local, un servidor, bajo costo.
   Alternativas: microservicios (operacion costosa); serverless (requisito local).
   Decision: un proceso Node con Express + Vite middleware.
   Consecuencias: arranque simple; SPOF; escalado vertical o multiples instancias
   sin estado (aun sin balanceador en el repo). server.ts:13,230-249.

 ADR-03 | Gemini 2.5 Flash + motor heuristico de respaldo ................. [R]
   Contexto: calidad de IA sin garantizar disponibilidad/cuota.
   Alternativas: solo IA (caidas); solo reglas (calidad baja).
   Decision: try Gemini -> catch -> fallback por nivel.
   Consecuencias: la sesion nunca se corta; el campo `model` identifica el motor.
   server.ts:21-29,59-101. Modelo: gemini-2.5-flash (server.ts:66,129).

 ADR-04 | Sin base de datos en v1.0, con DER preparado .................... [R]
   Contexto: alcance sin persistencia (Fase3/4).
   Alternativas: SQLite desde el inicio (postergada); Postgres (descartada).
   Decision: estado en React (useState) + DER de 13 tablas en el SRS.
   Consecuencias: demo simple; al activar persistencia cambian proyectos,
   historial y chat. App.tsx:26-31.

 ADR-05 | Limites duros de ingesta ...................................... [S/R]
   Contexto: techo de memoria del navegador y del body HTTP.
   Decision: 200 MB ZIP (texto de UI), 300 archivos, 4 MB de texto, 6 KB por
   archivo, 48 KB de muestra, 30 dependencias; express.json a 10 MB.
   Consecuencias: costos acotados; proyectos grandes se analizan parcialmente.
   analyzeProject.ts:66-69,134-163; server.ts:18. Los limites de ZIP no se
   aplican porque la carga real no esta cableada.

 ADR-06 | Sanitizacion del Markdown del chat ............................. [R por diseno]
   Contexto: la IA puede devolver HTML malicioso.
   Alternativas: render crudo (XSS); texto plano (pierde legibilidad).
   Decision vigente en codigo: el contenido se muestra como texto con
   `whitespace-pre-wrap` (ChatAsistenteIA.tsx:287); no hay
   dangerouslySetInnerHTML ni libreria Markdown. Riesgo mitigado por diseño.
   Consecuencias: seguros hoy; si se introduce un renderizador Markdown habra
   que anadir allowlist (Fase4 ADR-06).

 ADR-07 | Contrato de errores uniforme .................................. [R]
   Contexto: varios endpoints y clientes.
   Decision: { error: string } con 400 (falta message/code) y 500.
   Consecuencias: cliente simple; 413 se menciona en diseno pero express.json
   devuelve su propio formato. server.ts:44,112,151,225.

 ADR-08 | Navegacion por estado en una SPA ............................... [R]
   Contexto: 12 vistas, sin recarga.
   Alternativas: router con URLs (postergado); multipagina (descartada).
   Decision: ViewType en useState + Sidebar.
   Consecuencias: navegacion instantanea; sin deep links. App.tsx:26,44-49.

 ADR-09 | Configuracion por entorno y arranque tolerante ................. [R]
   Contexto: la key puede faltar o ser invalida.
   Decision: dotenv + try/catch en GoogleGenAI + PORT configurable.
   Consecuencias: siempre arranca; el "modo IA" NO se publica en /api/health
   porque el endpoint no existe (ver 6.8). server.ts:8,15,21-29.

 ADR-10 | Integracion CVE con timeout, cache y degradacion ............... [P]
   Contexto: fuente externa con latencia y caidas.
   Decision: timeout 5 s, cache TTL 24 h, respuesta vacia con aviso.
   Consecuencias: vista de riesgos no se bloquearia; hoy usa datos fijos.

 ADR-11 | Persistencia SQLite/Postgres cuando se active ASR-06 ........... [P]
   Decision: SQLite para v1.1 local, Postgres si se activa multiusuario.
   Consecuencias: aparece la capa de repositorio y migraciones.

 ADR-12 | Multiusuario con JWT cuando se active ASR-07 ................... [P]
   Decision: access token corto + refresh; user_id en todas las tablas.
   Consecuencias: disenar la BD con user_id desde el principio para no migrar
   dos veces. Hoy no hay login ni autorizacion.

 ADR-13 | Adaptador de ingesta por proveedor Git ........................ [P]
   Decision: interfaz comun fetchRepo(url, branch) -> zip.
   Consecuencias: agregar GitLab/Bitbucket no toca el analizador. Hoy el
   selector de motor AST del modal (tree-sitter/babel/syn) es decorativo.

 Decision arquitectonica transversal (no numerada en Fase4): exportar por Blob
 en el navegador evita otro endpoint de descarga y mantiene el servidor simple.

 5. ESTRATEGIA DE CALIDAD, SEGURIDAD Y RESILIENCIA
================================================================================

 5.1. MECANISMOS DE SEGURIDAD
   Implementado [R]:
     - La clave GEMINI_API_KEY se lee con dotenv solo en server.ts:22 y se pasa
       al constructor de GoogleGenAI; nunca se serializa al cliente.
     - .env y .env.* ignorados por Git, salvo .env.example (AGENTS.md y README).
     - El body JSON esta limitado a 10 MB (server.ts:18).
     - La respuesta de IA se muestra como texto, sin HTML inyectado.
     - Los mensajes de error son genericos ("Internal server error..."), sin
       trazas ni secretos (server.ts:104,151,226).
   No implementado [P] (riesgos abiertos):
     - Sin autenticacion/autorizacion: cualquier proceso local puede llamar
       a los endpoints (no hay JWT/OIDC/RBAC).
     - Sin CORS configurado: funciona porque frontend y API comparten origen;
       conviene fijar politica explicita si se separan.
     - Sin rate limiting: un cliente puede agotar cuota de Gemini.
     - Sin validacion de esquemas (zod/class-validator): solo se comprueba que
       `message`/`code` existan; el resto del body se confia.
     - Sin sanitizacion central de Markdown; hoy no hace falta por el render
       en texto, pero es deuda latente (ADR-06).
     - Sin cifrado en reposo (no hay reposo) ni en transito mas alla de lo que
       proporcione el hosting.
   Modelo STRIDE aplicado (resumen):
     Spoofing        : abierto (sin login) -> ADR-12.
     Tampering       : mitigado parcialmente por body limit y tipos TS en cliente;
                       sin validacion server-side de campos -> P0.
     Repudiation     : sin auditoria; el historial es de ejemplo -> P1.
     Info disclosure : clave protegida; codigo del usuario no se envia [S] -> P1.
     DoS             : sin rate limit; 10 MB por request -> P0.
     Elevation       : no existe modelo de permisos -> fuera de alcance v1.

 5.2. ESTRATEGIA DE PRUEBAS (QA)
   Hoy [R]: `npm run lint` = `tsc --noEmit` (package.json:12). Es la unica
   comprobacion automatica. No hay script "test", fixtures ni CI.
   Pruebas manuales recomendadas (verificables sin infraestructura):
     T-01 POST /api/gemini/chat sin message -> 400 {error:"Message is required"}.
     T-02 POST /api/gemini/chat con level="basico" y GEMINI_API_KEY ausente ->
          200 con model="codeexplain-core-v2.4".
     T-03 POST /api/gemini/explain sin code -> 400.
     T-04 POST /api/gemini/document con docType="c4" -> contenido @startuml.
     T-05 GET / -> index.html (dev via Vite, prod via dist/).
     T-06 body > 10 MB -> error de payload.
   Fitness functions propuestas para-evitar-regresiones arquitectonicas:
     - "Todo endpoint llamado por el cliente existe en server.ts": buscar
       fetch('/api/...') en src/ y compararlo con app.post/app.get en server.ts
       (hoy falla: /api/analyze y /api/analyze-url).
     - "Sin secretos en el frontend": grep GEMINI_API_KEY en src/ debe dar 0.
     - "Sin async sin manejo de error en endpoints": cada app.post debe tener
       try/catch y responder {error:...}.
     - "Sin setInterval en la ingesta": UploadModal.tsx debe usar el digest real.
     - "Puerto 3100": ningun archivo debe fijar 3000.
   Nota: ejecutar `npm run lint` antes de cerrar cualquier tarea (AGENTS.md).

 5.3. MONITOREO Y OBSERVABILIDAD
   Hoy [R]: console.log al arrancar (server.ts:247), console.warn en fallos de
   Gemini/fallback (server.ts:27,73,136) y console.error en errores 500
   (server.ts:103). No hay logs estructurados, metricas ni trazas.
   Ausente [P]: GET /api/health,Prometheus/Grafana, ELK, OpenTelemetry,
   correlation-id y medicion de latencia p95. Los Escenarios de Fase4 que dan
   por supuesto /api/health no son verificables hoy.
   Impacto: no es posible confirmar desde fuera si el motor activo es Gemini o
   fallback, aunque el campo `model` de la respuesta lo sugiere.

 5.4. RESILIENCIA Y RECUPERACION
   - Fallback de IA [R]: degradacion graceful, la sesion no se corta.
   - Arranque tolerante [R]: sin key la app sigue levantando.
   - SPOF [riesgo]: un proceso; si cae, cae UI y API juntos.
   - Sin timeout en la llamada a Gemini: una respuesta lenta bloquea el handler
     (Express es asincrono, pero no hay AbortController ni limite de tiempo).
   - Sin retry, backoff, circuit breaker, bulkhead ni DLQ propios (los textos
     "Redlock", "DLQ", "429 Retry-After" son ejemplos generados, no codigo).
   - RPO/RTO: no aplican hoy porque no hay estado persistente; deberan
     definirse en cuanto se active ADR-11.
   - Recomendacion P1: timeout de 8-10 s + AbortController, healthcheck real,
     y un circuit breaker simple antes de añadir BD.
