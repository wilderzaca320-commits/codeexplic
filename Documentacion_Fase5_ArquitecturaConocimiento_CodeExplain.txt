COMO LEER ESTE DOCUMENTO
- K1 = conocimiento sobre el software ANALIZADO (el proyecto del usuario).
- K2 = conocimiento sobre CodeExplain mismo (documentacion del producto).
- KU = Knowledge Unit (unidad atomica de conocimiento).
- Los codigos de taxonomia son estables y se usan en metadatos y busqueda:
  K1.PRY.ARQ.MOD, K2.PRD.SRS, etc.
- Todo se apoya en entidades reales de la app (ProjectWorkspace, MonitoredRepo,
  QueryHistoryItem, DatabaseTable, UseCaseItem, RiskItem, ChatMessage).
- [P] = propuesto, aun no implementado.


==============================================================================
 1. PROPOSITO Y ALCANCE
==============================================================================

1.1 PROBLEMA QUE RESUELVE
Hoy CodeExplain produce informacion valiosa pero dispersa:
  - El analisis vive en el estado de React y se pierde al recargar.
  - Cada vista muestra su propia copia de los datos (mock o calculada).
  - El chat y la documentacion no citan la evidencia que los origina.
  - No hay un vocabulario comun: "repo", "proyecto" y "workspace" se usan
    como sinonimos; "riesgo", "hallazgo" y "deuda" se mezclan.
  - La documentacion del producto (fases 1 a 4) esta en archivos sueltos sin
    enlaces entre si.
Resultado: el conocimiento no se encuentra, no se reutiliza y no se puede
auditar. Esta fase define como organizarlo.

1.2 ALCANCE
  Dentro:
  - Taxonomia y jerarquia de los dos dominios (K1 y K2).
  - Tesauro y vocabulario controlado.
  - Metadatos obligatorios y etiquetado.
  - Modelo de dominio y flujos del conocimiento.
  - Decision de granularidad (micro-contenido vs documento completo).
  - Seleccion de herramientas y arquitectura de busqueda/navegacion.
  - Mapa de conocimiento (grafo conceptual).
  Fuera:
  - Implementacion de la base de datos fisica (Fase 3, DER 4.5).
  - Diseno visual detallado de las 12 vistas.
  - Entrenamiento o fine-tuning de modelos.

1.3 PRINCIPIOS (rigen todas las decisiones)
  P1. Una entidad = un identificador estable. Nada se referencia por nombre.
  P2. Evidencia antes que opinion: toda afirmacion (KU) apunta a una fuente.
  P3. Micro-contenido atomico + composicion: se guarda pequeno, se muestra
      compuesto.
  P4. Vocabulario controlado: un concepto, un termino preferido, un codigo.
  P5. Enlaces explicitos: toda relacion es una arista con tipo y direccion.
  P6. Metadatos obligatorios: sin metadatos minimos, la unidad no se publica.
  P7. Degradacion sin IA: el conocimiento estructurado funciona aunque el
      motor heuristico reemplace a Gemini.

1.4 RELACION CON LAS FASES ANTERIORES
  Fase 1 -> necesidades que originan el conocimiento (que duele).
  Fase 2 -> 15 modulos que producen/consumen conocimiento.
  Fase 3 -> entidades del DER y 85 requerimientos (que se guarda).
  Fase 4 -> ASR/ADR que restringen donde vive el conocimiento (cliente,
            digest-only, sin BD en v1).
  Fase 5 -> este documento: como se organiza, busca y reutiliza.

2.4 REGLAS DE LA TAXONOMIA
  T1. Profundidad maxima 4 (dominio -> dimension -> tipo -> instancia).
  T2. Nombres en singular y sin sinonimos ("modulo", no "modulos/componentes").
  T3. Un nodo pertenece a un unico padre; las relaciones cruzadas se modelan
      como enlaces, no como pertenencia.
  T4. Los codigos son estables: no cambian si cambia el nombre visible.
  T5. Toda instancia hereda el contexto del padre (proyecto y dominio).
  T6. Si un nodo no tiene instancias, se marca como "vacio" y no se muestra
      en la navegacion (evita vistas huerfanas).

 3. TESAURO / VOCABULARIO CONTROLADO
==============================================================================

3.1 REGLAS DEL TESAURO
  - Cada concepto tiene UN termino preferido (USE).
  - Los sinonimos se registran como UF (used for) y no se usan en la UI ni en
    los metadatos.
  - Relaciones: BT (broader term / mas amplio), NT (narrower / mas especifico),
    RT (related / relacionado).
  - Cada termino tiene una nota de alcance (scope note) que aclara que SI y
    que NO incluye.
  - El tesauro se inyecta en los prompts de IA para que las respuestas usen
    el mismo vocabulario que la interfaz.

3.3 EL CASO "USUARIO vs CLIENTE vs COMPRADOR"
  En CodeExplain el dominio es analisis de software, NO comercio. Por eso:
  +-------------+----------------------------------------------------------+
  | Termino     | Uso correcto en CodeExplain                              |
  +-------------+----------------------------------------------------------+
  | usuario     | Persona que usa la app (desarrollador, estudiante,       |
  |             | arquitecto, docente, dueno, administrador).              |
  | cliente     | Organizacion duena de un proyecto analizado (empresa).   |
  |             | Se usa solo en contexto comercial/regulatorio.           |
  | comprador   | NO se usa en CodeExplain. Pertenece al dominio del       |
  |             | software analizado (e-commerce), no al producto.         |
  +-------------+----------------------------------------------------------+
  Regla: en la UI y en los prompts se dice "usuario"; "cliente" solo aparece
  en textos legales/comerciales; "comprador" se reserva para cuando el
  proyecto analizado sea una tienda.

3.4 TERMINOS AMBIGUOS Y SU REEMPLAZO
+---------------------------+---------------------------+-----------------------------+
| Se escribe hoy            | Problema                  | Estandar                    |
+---------------------------+---------------------------+-----------------------------+
| repo / workspace / app    | Tres nombres, un concepto | proyecto (o repositorio)    |
| componente / modulo       | Mezcla nivel de codigo    | modulo                      |
| bug / issue / problema     | Sin severidad ni evidencia| riesgo o vulnerabilidad     |
| deuda / TODO / pendiente  | Sin horas ni impacto      | deuda tecnica               |

| chat / consulta / prompt  | Tres artefactos distintos | mensaje / consulta / prompt |
| documento / entregable    | Mezcla salida y proceso   | documento                   |
| IA / modelo / motor       | Confunde proveedor y modo | motor (Gemini o fallback)   |
+---------------------------+---------------------------+-----------------------------+

3.5 RELACIONES DEL TESAURO (extracto)
  conocimiento
    BT-> proyecto
    NT-> hallazgo, documento, conversacion
  hallazgo
    NT-> riesgo, deuda tecnica, patron
  riesgo
    NT-> vulnerabilidad
    RT-> CVE, severidad, mitigacion
  arquitectura
    NT-> modulo, dependencia, acoplamiento, diagrama
  datos
    NT-> tabla, columna, relacion, migracion
  comportamiento
    NT-> caso de uso, escenario, endpoint, flujo

3.6 USO DEL TESAURO
  - UI: labels, filtros y tooltips usan el termino preferido.
  - Busqueda: los sinonimos se expanden a la consulta (repo -> proyecto).
  - IA: el system prompt incluye el glosario y prohibe los sinonimos.
  - Documentos: las plantillas usan los codigos y terminos del tesauro.
  - Metadatos: el campo `tipo` solo acepta valores del vocabulario (3.2).

4.2 VOCABULARIOS CONTROLADOS
  tipo        : proyecto, repositorio, analisis, modulo, dependencia, tabla,
                columna, caso_uso, escenario, riesgo, vulnerabilidad, deuda,
                spof, documento, plantilla, consulta, mensaje, prompt, ku.
  estado      : borrador, en_revision, validado, obsoleto.
  nivel       : basico, intermedio, avanzado, na.
  confianza   : alta (evidencia directa), media (inferencia IA),
                baja (heuristico sin evidencia).
  sensibilidad: publico, interno, restringido.
  retencion   : sesion, 30d, 90d, permanente.
  severidad   : alta, media, baja (solo riesgo/vulnerabilidad).
  categoria   : arquitectura, datos, comportamiento, calidad, documentacion,
                conversacion, operacion.

    "etiquetas": ["seguridad", "pagos", "webhook"],
    "enlaces": [
      {"rel": "afecta", "destino": "01J8Z3CCCCCCCCCCCCCCCCCCCC"},
      {"rel": "evidencia", "destino": "01J8Z3BBBBBBBBBBBBBBBBBBBB"}
    ],
    "hash_contenido": "9f2c...",
    "modelo": "gemini-2.5-flash"
  }

4.5 REGLAS DE ETIQUETADO
  E1. Minimo 3 etiquetas, maximo 8, tomadas del vocabulario controlado.
  E2. Prohibido inventar etiquetas libres; si falta una, se propone y se
      aprueba en el tesauro.
  E3. La etiqueta de proyecto se hereda automaticamente (no se repite).
  E4. `sensibilidad=restringido` obliga a `retencion=sesion`.
  E5. Toda KU de K1 debe tener `fuente_id`; sin fuente no se valida.
  E6. `confianza=baja` no puede pasar a `estado=validado` sin revision humana.

4.6 CALIDAD DE METADATOS
  - Completitud minima para publicar: 90% de campos obligatorios.
  - Validacion en el alta: tipo, estado, nivel y etiquetas contra vocabulario.
  - Deteccion de duplicados por hash_contenido + similitud de titulo.
  - Reporte semanal de metadatos incompletos (ver seccion 11).

5.2 DIAGRAMA CONCEPTUAL
  +-----------+       +-------------+       +--------------+       +-----------+
  | Usuario   |1     N| Proyecto    |1     N| Repositorio  |1     N| Analisis  |
  +-----------+-------+-------------+-------+--------------+-------+-----------+
                            |1                                          |1
                            |                                           |N
              +-------------+-------------+                   +---------+---------+
              |             |             |                   |                   |
              v             v             v                   v                   v
        +-----------+ +-----------+ +-----------+       +-----------+       +-----------+
        | Modulo    | | TablaBD   | | CasoDeUso |       | Hallazgo  |       | Documento |
        +-----------+ +-----------+ +-----------+       +-----------+       +-----------+
              |             |1            |1                  |                   |
              |             |N            |N                  |                   |
              |             v             v                   v                   v
              |       +-----------+ +-----------+       +-----------+       +-----------+
              |       | Columna   | | Escenario |       | Evidencia |       | Plantilla |
              |       +-----------+ +-----------+       +-----------+       +-----------+
              |                                             ^
              |                                             |
        +-----------+       +-------------+                 |
        | Consulta  |1     N| Mensaje     |-----------------+
        +-----------+-------+-------------+
              |
              v
        +-----------+
        | Etiqueta  | (N:M con KU)
        +-----------+

  Relaciones clave:
  - Un Proyecto tiene N Repositorios y N Analisis.
  - Un Analisis produce N Hallazgos (riesgo, deuda, patron).
  - Todo Hallazgo apunta a una Evidencia (archivo + lineas o endpoint).
  - Un Documento se compone de KUs y usa una Plantilla.
  - Una Consulta agrupa Mensajes; ambos pueden citar KUs.
  - Las Etiquetas clasifican cualquier KU (N:M).

5.3 FLUJOS DEL CONOCIMIENTO
  F1 Captura (ingesta)
     Archivo/URL -> Repositorio -> Digest -> Analisis.
     Se guarda: proyecto, repositorio, analisis, evidencia de entrada.
  F2 Clasificacion (analisis)
     Analisis -> Hallazgos (KU) -> Etiquetas -> Enlaces a evidencia.
     Se aplica el tesauro y se asigna codigo de taxonomia.
  F3 Consulta (uso)
     Usuario -> Consulta -> Mensaje -> Respuesta (Gemini/fallback).
     La respuesta cita KUs y evidencias cuando existen.
  F4 Composicion (documentacion)
     Plantilla + KUs del proyecto -> Documento -> Version -> Export.
  F5 Reutilizacion
     KU validada -> vista / documento / prompt / otro proyecto (solo patrones).
  F6 Retiro
     KU obsoleta -> estado=obsoleto -> se conserva por trazabilidad y se
     excluye de busquedas y composiciones.

5.4 REGLAS DE INTEGRIDAD
  I1. Una KU pertenece a un solo proyecto (K1) o al producto (K2).
  I2. Ninguna KU se publica sin evidencia (fuente_id).
  I3. Un documento generado siempre referencia las KUs que lo componen.
  I4. Un riesgo puede convertirse en deuda o en caso de uso, pero no se
      duplica: se enlaza con `rel=deriva_de`.
  I5. Borrar un proyecto marca sus KUs como obsoletas; no se borran en cascada
      si son evidencia de un documento publicado.
  I6. Los enlaces son dirigidos y tipados; el backlink se calcula, no se
      almacena dos veces.

5.5 TRIPLE ETIQUETA EPISTEMICA (hecho / inferencia / opinion)
  Toda KU declara su naturaleza:
  +-------------+----------------------------------------------+----------------+
  | Naturaleza  | Significado                                  | Confianza      |
  +-------------+----------------------------------------------+----------------+
  | hecho       | Verificado en el codigo o la configuracion   | alta           |
  | inferencia  | Deduccion de la IA o del analisis estatico   | media          |
  | opinion     | Recomendacion o buena practica               | baja           |
  +-------------+----------------------------------------------+----------------+
  Regla: una `opinion` nunca se muestra como `hecho`; la UI usa iconos y
  colores distintos, y los documentos separan "Hallazgos" de "Recomendaciones".

 6. GRANULARIDAD
==============================================================================

6.1 NIVELES DE GRANULARIDAD
+------+---------------------+------------------------------------------+---------------------------+
| Nivel| Unidad              | Ejemplo                                  | Se almacena?              |
+------+---------------------+------------------------------------------+---------------------------+
| L0   | Fuente / evidencia  | server.ts lineas 59-75                   | Si (hash + ruta)          |
| L1   | KU atomica          | "payments depende de redis"              | Si (unidad base)          |
| L2   | Ficha de entidad    | Ficha del modulo payments (N KUs)        | Si (vista materializada)  |
| L3   | Vista de conocimiento| Vista Arquitectura, vista BD, chat       | Se compone al vuelo       |
| L4   | Documento           | README, OpenAPI, C4, ADR                 | Si (versionado + checksum)|
+------+---------------------+------------------------------------------+---------------------------+

6.2 DECISION DE GRANULARIDAD (KD-01)
  Se almacena en L1 (KU atomica) y L2 (ficha), y se compone L3/L4 bajo demanda.
  Motivos:
  - Reutilizacion: una KU sirve para la vista, el chat y el documento.
  - Busqueda: se indexa la afirmacion, no el documento completo.
  - Consistencia: cambiar una KU actualiza todas las composiciones.
  - Costo: no se duplica el mismo texto en 4 documentos.
  - Trazabilidad: cada frase del README se puede rastrear a una evidencia.

6.3 TRADE-OFFS
+---------------------------+---------------------+---------------------+---------------------+
| Criterio                  | Documento completo  | Micro-contenido     | Hibrido (elegido)   |
+---------------------------+---------------------+---------------------+---------------------+
| Facilidad de redaccion    | Alta                | Baja                | Media               |
| Reutilizacion             | Baja                | Alta                | Alta                |
| Busqueda                  | Baja (texto largo)  | Alta                | Alta                |
| Consistencia al cambiar   | Baja (copias)       | Alta                | Alta                |
| Costo de curacion         | Bajo                | Alto                | Medio               |
| Trazabilidad a evidencia  | Baja                | Alta                | Alta                |
+---------------------------+---------------------+---------------------+---------------------+

6.4 REGLAS DE ATOMICIDAD
  A1. Una KU = una afirmacion verificable (no dos ideas unidas por "y").
  A2. Titulo <= 120 caracteres; claim <= 500.
  A3. Si una KU necesita mas de una evidencia, se parte en dos y se enlazan.
  A4. La KU no repite el contexto del proyecto (se hereda por metadatos).
  A5. Deduplicacion: mismo proyecto + mismo claim normalizado = una sola KU.
  A6. Las KUs no se editan en los documentos: se editan en la fuente y la
      composicion se regenera.

6.5 COMPOSICION DE DOCUMENTOS
  Plantilla README =
    seccion "Vision"      <- KUs de K1.PRY.CTX.VIS
    seccion "Stack"       <- KUs de K1.PRY.CTX.STK
    seccion "Arquitectura"<- KUs de K1.PRY.ARQ.MOD + ARQ.DEP
    seccion "Datos"       <- KUs de K1.PRY.DAT.TAB
    seccion "Riesgos"     <- KUs de K1.PRY.CAL.RIE
    seccion "Uso"         <- KUs de K2.PRD.MAN.INS (si aplica)
  Regla: la plantilla define el orden y el tono; las KUs definen el contenido.
  Si falta una seccion, se marca "sin informacion" en vez de inventar.

6.6 EJEMPLO DE COMPOSICION
  KU-00042: "El modulo payments depende de redis para idempotencia."
  KU-00043: "El webhook no valida la firma antes de procesar."
  KU-00044: "Se estiman 120 h de deuda en la integracion de pagos."
  README (fragmento):
    ## Arquitectura
    El modulo payments depende de redis para idempotencia (KU-00042).
    ## Riesgos
    El webhook no valida la firma antes de procesar (KU-00043).
    ## Deuda tecnica
    Se estiman 120 h de deuda en la integracion de pagos (KU-00044).

    Producto > Fase 4 > ARD > ADR-01

  - El ultimo nivel no es enlace.

8.4 INDICE DE BUSQUEDA
  Campos indexados (peso):
    titulo (5), etiquetas (4), claim (3), codigo_taxonomia (3),
    nombre_entidad (3), resumen (2), contenido (2), evidencia (1).
  Filtros: dominio, proyecto, tipo, dimension, severidad, estado, nivel,
    lenguaje, autor, fecha.
  El indice se reconstruye al cambiar el estado (alta, edicion, retiro).

8.5 FACETAS
  - Dominio: K1 / K2.
  - Proyecto: uno o varios (solo K1).
  - Tipo: modulo, riesgo, deuda, tabla, caso de uso, documento...
  - Dimension: contexto, arquitectura, datos, comportamiento, calidad,
    documentacion, conversacion.
  - Estado: borrador, validado, obsoleto.
  - Nivel: basico, intermedio, avanzado.
  - Severidad: alta, media, baja (solo riesgos).
  Las facetas muestran conteo y se combinan con AND.

8.6 RANKING (formula simple y explicable)
  score = 5*titulo + 4*etiqueta + 3*claim + 3*codigo + 3*entidad
        + 2*resumen + 2*contenido + 1*evidencia
        + 0.5*recencia + 0.5*confianza_alta
  Desempate: estado validado > borrador; luego fecha descendente.
  Sin IA en v1: ranking determinista y auditable.

8.7 SINTAXIS DE CONSULTA
  - Texto libre: `acoplamiento pagos`
  - Campo: `tipo:riesgo severidad:alta`
  - Proyecto: `proyecto:opencommerce`
  - Etiqueta: `tag:seguridad`
  - Estado: `estado:validado`
  - Combinacion: `tipo:deuda estado:borrador proyecto:opencommerce`
  - Frase exacta: `"idempotencia distribuida"`
  - Rango: `fecha:[2026-11-01 TO 2026-11-11]`

8.8 EXPANSION DE SINONIMOS (tesauro)

  doc / entregable              documento
  La expansion se muestra como "Se busco tambien: ..." para que sea
  transparente.

8.9 ENLACES INTERNOS Y BACKLINKS
  - Cada artefacto tiene un panel "Relacionado" con:
      evidencia (fuente), derivados (KUs), documentos que lo citan y
      vistas donde aparece.
  - Reglas: enlace con tipo; sin enlaces a nodos obsoletos (se muestran
    tachados); backlinks calculados desde `edges`.
  - En el chat, cada respuesta puede citar `[KU-00042]` y abrir la ficha.

8.11 ESTADOS VACIOS

    quitar filtros + enlace al glosario.
  - Proyecto sin analisis: "Analiza el proyecto para generar conocimiento".

8.12 METRICAS DE BUSQUEDA

  - Tiempo hasta el primer clic < 15 s.

    navegacion).
  - Uso de facetas por sesion.

  Nodos totales del mapa: 62 (1 CE + 2 dominios + 12 dimensiones + 47 tipos).
  Aristas de contencion: 61 (una por nodo, excepto CE).
  Aristas cruzadas: 12 (ver 9.2 y 7.5).
  Aristas tipadas : 10 (evidencia, depende_de, contiene, usa, afecta,
                    deriva_de, documenta, cita, contradice, reemplaza).
  Profundidad     : 4 niveles (dominio > dimension > tipo > instancia).
  Nodos tipicos por proyecto: 150-400 (un proyecto mediano).
  Nodos K2        : 5 fases + 85 requerimientos + 18 ASR + 13 ADR + manual.

9.4 VERSION VISUAL
  Archivo: `Mapa_Conocimiento_CodeExplain.html`
  - Grafo interactivo en SVG, sin dependencias externas (offline).
  - Nodos agrupados por dominio, con color por tipo.
  - Al pasar el mouse se resaltan las aristas conectadas.
  - Al hacer clic se abre una ficha con: codigo, definicion, ejemplo de
    metadatos y enlaces.
  - Incluye leyenda, buscador simple y boton "centrar".
  - Se abre en el navegador; sirve como anexo visual del documento.

9.5 MANTENIMIENTO DEL MAPA
  - El mapa no se dibuja a mano: se genera desde la tabla `edges`.
  - Alta de un nodo = alta de una fila en `nodes` con su codigo.
  - Revision mensual: nodos huerfanos (sin arista) y enlaces rotos.
  - El HTML es una proyeccion de solo lectura; la fuente es el JSON/SQLite.

 10. REUTILIZACION DEL CONOCIMIENTO
==============================================================================

10.1 MATRIZ ARTEFACTO -> REUTILIZACION
+---------------------------+--------------------------------------+---------------------------+
| Artefacto (KU)            | Se reutiliza en                     | Mecanismo                 |
+---------------------------+--------------------------------------+---------------------------+
| Glosario / tesauro        | UI, prompts IA, documentos           | inyeccion + tooltips      |
| KU de modulo              | vista arquitectura, C4, README, chat | composicion por codigo    |
| KU de tabla/columna       | vista BD, OpenAPI, README            | plantilla + secciones     |
| KU de caso de uso         | vista CU, Gherkin, README            | composicion               |
| KU de riesgo              | vista riesgos, ADR, informe de deuda | enlace + seccion          |
| KU de deuda               | vista deuda, informe exportable      | agregacion por proyecto   |
| Evidencia (fuente)        | auditoria, confianza, trazabilidad   | cita con hash y lineas    |
| Plantilla de documento    | generador, export, chat              | seleccion por doc_type    |
| Prompt por nivel          | chat, explain, documentos            | biblioteca de prompts     |
| Consulta validada         | historial, FAQ, onboarding           | promocion a KU            |
+---------------------------+--------------------------------------+---------------------------+

10.2 PLANTILLAS Y SNIPPETS
  - Plantilla de documento: README, OpenAPI, C4, ADR (ya existen en RF-BE-20).
  - Snippet de codigo: bloque reutilizable con lenguaje y evidencia.
  - Snippet de riesgo: categoria + severidad + mitigacion + evidencia.
  - Snippet de metrica: nombre + valor + unidad + fecha + fuente.
  Regla: un snippet no se copia; se referencia por ID para que las
  actualizaciones se propaguen.

10.3 BIBLIOTECA DE PROMPTS POR NIVEL
  - `prompt.basico.v1`, `prompt.intermedio.v1`, `prompt.avanzado.v1`
    (alineados con LEVEL_PROMPTS de server.ts).
  - Versionados y con metadatos: nivel, objetivo, tono, prohibiciones.
  - Se inyectan junto con el glosario para evitar sinonimos.
  - Se pueden probar contra un set de preguntas de referencia.

10.4 PATRONES ENTRE PROYECTOS
  - Solo se comparten patrones anonimos, nunca codigo ni datos del cliente.
  - Un patron es una KU de K1 promovida a K2 con `sensibilidad=publico`.
  - Requiere revision humana y consentimiento (C-REG-02).
  - Ejemplo: "webhook sin validacion de firma" como patron de riesgo.

10.5 CICLO DE VIDA
  Capturar -> Clasificar -> Enlazar -> Validar -> Reutilizar -> Retirar
  1. Capturar: ingesta o consulta genera una KU candidata.
  2. Clasificar: tipo, codigo de taxonomia, etiquetas, nivel.
  3. Enlazar: evidencia, entidad afectada, documentos que la citan.
  4. Validar: revision humana si confianza < alta.
  5. Reutilizar: aparece en vistas, documentos, prompts y busqueda.
  6. Retirar: estado=obsoleto; se conserva por trazabilidad.

 11. GOBERNANZA Y CALIDAD
==============================================================================

11.1 ROLES
+---------------------+-----------------------------------------------------------+
| Rol                 | Responsabilidad                                           |
+---------------------+-----------------------------------------------------------+
| Knowledge Owner     | Define taxonomia, tesauro y prioridades.                  |
| Curador             | Revisa KUs, valida, deduplica y retira.                   |
| Contribuidor        | Crea KUs desde analisis, chat o documentos.               |
| Consumidor          | Usa busqueda, vistas y documentos (no edita).             |
| Administrador TI    | Configura entorno, secretos y retencion.                  |
+---------------------+-----------------------------------------------------------+

11.2 VERSIONADO
  - KU: semver (1.0.0). Cambio de claim = major; correccion = minor;
    formato = patch.
  - Documento: version + checksum; se guarda el historial de generaciones.
  - Tesauro: versionado aparte; un cambio de termino afecta la busqueda y
    los prompts (se prueba antes de publicar).

11.3 REGLAS DE CALIDAD
  Q1. Toda KU tiene evidencia y codigo de taxonomia.
  Q2. Sin duplicados por hash_contenido.
  Q3. Sin enlaces rotos (validacion semanal).
  Q4. Sin sinonimos prohibidos en titulos y claims.
  Q5. Los documentos citan las KUs que los componen.
  Q6. Las opiniones estan separadas de los hechos.

11.4 METRICAS
+-----------------------------+----------------------------------+-------------------+
| Metrica                     | Formula                          | Objetivo          |
+-----------------------------+----------------------------------+-------------------+
| Cobertura                   | entidades con KU / entidades     | >= 80%            |
| Completitud de metadatos    | campos llenos / obligatorios     | >= 90%            |
| Nodos huerfanos             | nodos sin arista / total         | <= 5%             |
| Enlaces rotos               | rotos / total                    | 0                 |
| Duplicados                  | duplicados detectados            | 0                 |
| Reutilizacion               | KUs citadas en 2+ salidas / total| >= 40%            |
| Frescura                    | KUs sin revisar > 90 dias / total| <= 10%            |
| Busqueda sin resultados     | consultas con 0 resultados       | <= 10%            |
+-----------------------------+----------------------------------+-------------------+

11.5 RETENCION Y DEPRECACION
  - Codigo y evidencia: retencion=sesion (no se persiste en v1.0).
  - Consultas: 30d por defecto; el usuario puede borrarlas.
  - Documentos: permanentes mientras el proyecto exista.
  - K2 (producto): permanente y versionado.
  - Retiro: estado=obsoleto + motivo + fecha + reemplazo (si existe).
  - Derecho de eliminacion: borra KUs y evidencia del proyecto, conserva
    solo metricas agregadas y anonimas.
